# Architecture and modernization decisions

## Chosen pain point

The case study targets controlled legacy migration for a Japanese commerce client: vendor masters arrive as UTF-8 or CP932 CSV, valid and invalid records are mixed, a failed restart can duplicate work, and stakeholders need a numerical answer to “did the new system match the old one?”

This is deliberately different from a generic CRUD portfolio. The user-visible storefront proves the new system works, while the operations ledger exposes staging, quarantine, checkpoints, reconciliation, and fulfillment audit trails.

## Boundaries

- Next.js is the public UI and backend-for-frontend. It forwards only approved request headers and injects trust secrets server-side.
- Spring Boot owns business invariants. Direct mutations without the BFF secret are rejected.
- PostgreSQL is canonical for products, inventory, orders, migration checkpoints, reconciliation, and audit events.
- Redis accelerates catalog reads only. An outage reduces performance but does not reduce correctness.
- Cloudflare provides the free long-lived frontend edge. The backend is a portable OCI image; hosting is an environment choice, not application logic.

## Consistency choices

Checkout locks requested product and inventory rows in SKU order, matching the import lock order. All totals and inventory movements commit together. A transaction advisory lock serializes the physical key: SHA-256 of a domain-separated guest scope/operation/raw-key tuple. The scope is itself the hash of a browser-generated 256-bit guest capability, not a verified account. A canonical request hash rejects payload mismatch. Historical unscoped raw keys are blocked for review, not adopted into a new guest namespace. Create/recover/close use transaction-local 3s lock and 8s statement limits within a Spring 10s transaction; this is layered wait control, not hard end-to-end cancellation.

The shared datasource has 2s Hikari acquisition / 1s validation budgets and pgJDBC connect/login 3s, socket-read 15s, cancellation-channel 2s, TCP keepalive. These apply beyond checkout, so migration/import verification is required after changing them. JDBC/transaction exceptions are sanitized to backend 503 DATABASE_UNAVAILABLE; close-unused retains its existing 409 lock-contention contract. Unknown commit acknowledgement must still recover by the original key. Timeout values do not imply all waits finish before the BFF's 12s deadline, nor do they bound every OS/DNS/synchronous stall; deployment/connection-string overrides and long migrations need review.

The typed checkout coordinator persists operation identity and canonical payload/capability hashes before POST, never the customer payload or tracking token. It restores unresolved/confirmed/closed state after reload without automatic network replay. GET recovery returning 404 cannot release the identity. Closing an unused key and creation share the same per-key advisory lock, so a durable closure rejects a late original request with 410. Existing orders cannot be closed. A second shared advisory lock serializes closure capacity (10,000 retained hashes); no safety tombstones are evicted. This demo limit bounds table growth, not denial of service. Acknowledgement is explicit, and storage compare checks fence stale component responses. Request timeout is an unknown outcome, not cancellation. Browser storage is not a cross-device identity or tamper-proof ledger.

New tracking tokens use SecureRandom (32 bytes), not a hash of the idempotency key. The stored lookup hash remains compatible with legacy tracking. A separate backend-only AES-256-GCM key protects the replay copy, with random 12-byte IV, 128-bit tag and order-ID/domain AAD. New order IDs are random; raw guest capability/new request key and plaintext replay token are not stored in PostgreSQL. Wrong key, packet corruption, missing copy or hash disagreement fails replay closed; it does not rotate the token or repeat the sale. This uses standard JDK cryptography, not a custom token/JWT protocol. The key is stable server configuration; there is no active keyring/online re-encryption yet.

Replay is allowed while created_at is newer than DB clock minus 24 hours; creation timestamps also use DB time. The check is at lookup, not a hard guarantee that no response byte arrives after the boundary. Outside the window, the same key conflicts while the original tracking hash still works. A per-minute bounded transaction clears at most 100 expired replay ciphertexts under SKIP LOCKED (15s transaction, 3s lock, 10s statement limits). A partial index supports selection; orders/key hashes remain as tombstones for the lifetime of retained orders. No broader business-order retention/deletion policy or exact purge deadline is implied.

Imports use a byte checksum as logical identity. A PostgreSQL advisory transaction lock serializes concurrent checksum lookup+staging; unique identity is also enforced in the DB. Staging and work commit before async acknowledgement. Rows apply in independent groups of 50; duplicate normalized SKUs are all quarantined. Legacy feeds update metadata only; schema v2 stock adjustments compare exported expected versions under lock. Applied proof/movement/markers/counters commit together and metrics/cache invalidation run after commit. Checkpoint is progress, not the resume selector: valid unapplied markers decide remaining work.

The checksum namespace remains global/raw-byte for historical compatibility: source name is only a label, schema/vendor fields are part of the file bytes, and changing a label must not replay stock. Canonical encoding is checked even on a duplicate; a conflicting declared encoding returns 409. Actual byte/newline/encoding changes produce a different identity, so this is not semantic deduplication. UTF-8/CP932 decoding uses REPORT; duplicate headers, inconsistent row width and malformed syntax reject before staging. At most 1,000 records and 5,000,000 bytes are accepted. Structurally valid business errors still quarantine individual rows.

`RequestBodyLimitAdvice` bounds Spring controller body reads before conversion: byte-array CSV up to 5,000,000 bytes, JSON bodies up to 65,536 bytes. It checks declared length and counts actual read/skip bytes, consuming at most one overflow byte before throwing the 413-mapped exception. The BFF independently counts stream bytes and cancels oversize bodies; accepted bytes are forwarded unchanged. Application limits do not constrain all reverse-proxy/runtime buffering or provide read deadlines; servlet form login is outside RequestBodyAdvice and remains BFF-limited. Full timeout/ingress policy is still API-1 work.

Catalog Redis v2 stores metadata only; each request independently reads current PostgreSQL stock and active product/vendor eligibility, then merges by SKU. Cached inactive entries are filtered. New list entries/name/price may remain stale until metadata refresh, and after-commit invalidation still permits late reader fills. Five-minute TTL is per cache write, not a hard freshness bound measured from a mutation commit. Old v1 inventory-bearing entries are ignored. A catalog result is a non-reserving read snapshot; checkout always locks/reloads canonical price and stock. Fail-open cache exceptions fall back to PostgreSQL, not stale stock.

The UI requests `Prefer: respond-async`; the backend returns 202 and a durable job summary, not a promise of completion. The dispatcher claims one explicit async READY item per fixed-delay tick with job-row SKIP LOCKED, then uses the same fenced JobRunner/Batch identity as the compatibility synchronous path. No in-memory queue is required. Caught FAILED jobs can be requeued; completed replay is a no-op, active/busy jobs return 409. UI polls active recent jobs and offers manual refresh/FAILED restart, stopping automatic polling on read errors. Clients without the preference retain synchronous semantics for rollout compatibility.

Reconciliation compares applied baselines with current state. Higher versions mean changed since import, not automatically corruption or verified correctness. Stock without a comparable baseline is explicitly unverified. Same-version quantity/price drift and version regressions are discrepancies; reports never overwrite inventory. V5/V6 preserve historical jobs without inventing baseline proof. The matching frontend surfaces these limits rather than showing a blanket success for zero mismatches. See [local remediation evidence](evidence/remediation-2026-10-18.md); these changes have not been deployed yet.

## Import work ownership (V7)

New staging transactions also persist a work item. Job→work is the shared lock order for claims, chunks and terminal updates. Claims have random tokens, monotonically increasing generations and 60-second DB-clock leases. The tasklet resolves only its non-identifying execution generation; it cannot pick up a newer owner's token. Tokens are not JobParameters and therefore are not emitted by the launcher's parameter log. Business transactions verify the claim before writing and renew it before returning; invalid ownership rolls back the group. Failure/finalization uses the same fenced ownership checks.

Historical active work is BLOCKED, not assigned a fake lease. V8 explicitly marks dispatch intent so workers do not steal READY work from old synchronous callers. V9 adds recovery count/time/reason, not a fabricated historical owner. Old unfenced binaries must be drained/stopped before activating the new protocol; this is not a zero-downtime mixed-version rollout guarantee.

## Bounded abandoned-execution recovery (V9, local only)

The dispatcher first attempts one expired, explicitly async CLAIMED item with job-row SKIP LOCKED, then rechecks work under job→work locks. A matching active Batch execution and active steps are retired through the standard JDBC repository; ownership revocation (generation increment), metadata retirement and READY/STAGED requeue commit together. Applied markers are preserved. A prior lower-generation FAILED/STOPPED execution also permits recovery of a second crash after claim but before new execution creation. No execution exists yet is a valid pre-launch window. Completed metadata plus completed business state/no pending rows is acknowledged FINISHED without another execution. UNKNOWN/ABANDONED, generation mismatch or contradictory completion is BLOCKED for review. Three recoveries are allowed; a subsequent owner loss is blocked. Failed recovery transactions do not prevent unrelated READY work from dispatching, but a damaged recovery candidate can still require manual intervention.

All runtime job/step/launcher references explicitly use a fenced JobRepository. Each mutation verifies in-thread claim/job/generation, opens a bounded REQUIRES_NEW transaction, locks job/work and verifies lease before and after the delegate call. The standard JDBC factory uses REQUIRED so metadata and fence share the same connection/commit; recovery uses that raw delegate only inside its own locked transaction. The synchronous launcher is intentional: ThreadLocal scope is not propagated to arbitrary executors. Mutation without scope, stale job/step/context writes and deletion are rejected; reads remain ordinary metadata reads. Boot's framework repository is not used by the import runtime.

The empty chunk completes business bookkeeping but retains/renews CLAIMED ownership. Only after Batch metadata is COMPLETED does the runner validate business/metadata/pending state and release FINISHED. A crash before this acknowledgement can therefore be recovered without rerunning business changes. Tasklet restart is allowed even if its previous step completed, because the authoritative selector is valid unapplied rows, not the checkpoint count.

Metadata/recovery transactions have 15-second transaction, 3-second lock and 10-second statement limits. These are not full flow bounds: business chunk queries and ingress still need broader timeout/size policy, and renewal is per chunk, not an independent heartbeat. Real crash proof injects lease expiry and terminates an orphaned test-only sleeping query; no wall-clock availability claim or proof of all interleavings is made. Deploy requires V7–V9 and stopping old writers that bypass metadata fencing. Do not truncate Batch history/reset RUNNING blindly.

## Security and privacy

The BFF reads requests within a 10-second handler budget and applies a separate 12-second upstream deadline through complete response-body consumption. It buffers at most 5,000,000 response bytes before forwarding headers, preserving the ability to return structured 502/503/504 instead of a partial success. Upload byte limits remain CSV 5,000,000 / other bodies 65,536. Deadline abort cancels the fetch/reader without automatic mutation retry; it does not cancel Java's transaction. This is a bounded JSON/CSV proxy, not an SSE/download-streaming path. JSON syntax/UTF-8 is checked when declared as JSON, not application schema validation. Valid 4xx business responses are preserved; upstream 5xx and cookies on those failed responses are sanitized into generic unavailable responses. Backend-specific 503 codes are intentionally not exposed through this boundary.

These budgets do not cover time before handler invocation, synchronous event-loop stalls, aggregate concurrent memory or Java database lock/pool/query waits. Cold-start hosting may exceed a deadline; checkout must retain identity and use scoped recovery after availability returns. Response byte limits require pagination for sufficiently large operations/history exports; there is no unbounded buffering fallback.

Guest checkout intentionally supports invoice and cash-on-delivery only; no fake card processor is presented. Tracking responses exclude name, email, and address. Ops service credentials live only in the Next.js server environment and do not grant user access: operations also require a current OPERATOR account and JDBC session, plus CSRF on mutations. Production startup rejects short or known development secrets. Logs correlate by request ID and application audit details contain business identifiers, not customer PII.

## Supplier onboarding extension (V14, local only)

Immutable declarative integration profiles add strict supplier header mapping and a read-only preview before explicit confirmation. Preview reads canonical price/vendor and product/stock versions in one bounded query; a short-lived HMAC receipt binds approval to the operator, profile/version, original bytes and enrichment. New staging rechecks activation/freshness, records profile provenance/audit in the same job/work transaction, and preserves the existing global raw-byte checksum namespace. Different profiles/versions over identical bytes conflict, rather than replaying business effects.

The original parser, queue, Batch instance, chunk transactions, fencing, recovery and reconciliation are reused. Supplier rows additionally compare expected product version under the existing product/stock locks. Invalid text cells are not persisted for quarantined rows. Existing single-store OPERATOR/session/CSRF/trust boundaries remain; no tenancy, alternate queue or arbitrary scripts were added. A reviewed three-column file still needs operator assurance of business freshness; versions protect changes after review, not source age before it.

The feature has not been pushed/deployed; local Worker build is not hosting evidence.

## Evolution path

The same container can later run on AWS ECS/EKS. Terraform can be added when an AWS account exists, mapping PostgreSQL to RDS, Redis to ElastiCache, OTLP to the selected observability backend, and secrets to Secrets Manager. Deferring those resources avoids fake IaC that has never been applied.
